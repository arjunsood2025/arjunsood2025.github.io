LLM Platform: Pretraining, Post-Training, and a From-Scratch Inference Engine

Technologies: Python, PyTorch, Triton, DDP/FSDP2, DPO, lm-eval-harness, FastAPI, Prometheus, Docker

An LLM lab runs three systems: one to pretrain a base model, one to post-train it into an assistant, and one to serve it quickly. This project builds all three, with no model, trainer, or serving framework underneath. The byte-level BPE tokenizer, the transformer itself, the distributed training loop, the preference-tuning loss, and the inference engine are all written in the repository. The model is a 125M-parameter LLaMA-style decoder-only transformer (RMSNorm, SwiGLU, RoPE, GQA, and tied embeddings), trained on 1.26B tokens of FineWeb-Edu on a single RTX 5070. It sustained 42.7% MFU, meaning it kept the GPU's arithmetic units doing useful work 42.7% of the time they theoretically could be. Checkpoint resume is bitwise-deterministic, so an interrupted run restarts into exactly the numbers an uninterrupted one would have produced.

  • Replaced two hot PyTorch operations with hand-written Triton GPU kernels: a fused RMSNorm at 2.18× and a fused cross-entropy at 3.39×, both timed on forward plus backward at real training shapes. Fusing means doing the whole operation in one pass over GPU memory instead of several, and the cross-entropy kernel computes its logsumexp online so it never has to materialize the full logit matrix. Each kernel ships with a correctness test against the PyTorch reference and a microbenchmark. The data pipeline streams memory-mapped token shards. Its MinHash deduplication and n-gram contamination filters are implemented and unit-tested, but were not applied to this particular training run.
  • Ran a seven-run scaling study over a grid of 10M, 30M, and 85M parameters with matching token budgets, then fit the compute-loss power law L = E + A·C−α, which describes how loss falls as compute rises. The fit gave α = 0.195, and a Chinchilla-style joint fit gave a data exponent of 0.323 against the paper's 0.28. Holding compute fixed, RoPE beat learned positional embeddings by 0.30 nats, while SwiGLU and GQA tied their alternatives on loss. The GQA tie is the useful result, because matching the loss with a smaller KV cache means the same quality for less memory at serving time.
  • Post-trained in two stages. First, supervised fine-tuning on 30k conversations, using loss masking so the model is scored only on its own replies and sequence packing so batches are not padded with waste. Then a from-scratch DPO implementation on 4k preference pairs, which tunes the model toward the preferred response in each pair. DPO raised preference accuracy from 42% to 58% while holding KL divergence from the starting model near 0.10, so the gain did not come from drifting far off that policy. A separate LLM judge, position-debiased and reported with bootstrap confidence intervals, nevertheless preferred the SFT model slightly: DPO won 43.8% of comparisons, with a 95% interval of [37.5, 48.8]. The number is reported as measured rather than filtered for a favorable one.
  • Built the inference engine around a paged KV cache, which stores attention state in fixed-size blocks rather than one contiguous slab per sequence, so memory is not reserved for tokens a request may never generate. Chained-hash prefix caching lets requests sharing a prompt prefix share those blocks, with copy-on-write once they diverge. Together these raised maximum concurrency from 32 sequences to 170. The engine also does continuous batching with recompute preemption, speculative decoding that accepts 53% of draft tokens for 3.09 output tokens per target forward pass at k=4, and int8 weight-only quantization. Throughput reaches 433 output tokens per second at batch 128, served over streaming SSE and instrumented with Prometheus.
  • Pinned correctness with more than 65 tests in CI, all CPU-only so the suite runs without a GPU. The load-bearing cases assert that the engine's greedy output matches the reference implementation, that paged attention matches dense SDPA even when its blocks are shuffled, that preemption cannot change output, that incremental KV-cache decoding matches a single full forward pass, and that the DPO loss matches values computed by hand.

Raft-Replicated Key-Value Store with a From-Scratch LSM Engine

Technologies: Rust, Tokio, Raft Consensus, LSM Trees, Deterministic Simulation Testing, serde/bincode

A replicated key-value database written from scratch in Rust, covering the storage engine, the consensus layer, the networking, and the test infrastructure needed to show it is correct. It is linearizable, meaning clients can never catch the cluster contradicting itself: every operation appears to take effect at one instant, in an order consistent with real time. There are no database, consensus, or RPC crates involved; the entire dependency list is tokio, serde/bincode, and crc32fast. Storage is an LSM-tree engine, with a CRC-framed write-ahead log that detects and recovers from torn writes, bloom-filtered SSTables, leveled compaction, and MVCC snapshots. Above it sits a sans-IO Raft core, meaning the consensus logic is a pure state machine that takes in messages and timer ticks and returns actions, with every socket and disk call handled outside it. That core implements pre-vote elections, pipelined replication, InstallSnapshot, membership changes, and ReadIndex.

  • Built a deterministic simulator in the style of FoundationDB. The entire cluster, including nodes, disks, network, and clients, runs single-threaded on virtual time driven by a single seeded PRNG. It injects message loss, duplication, and reordering, asymmetric partitions where one node can reach another but not the reverse, crash-restart that wipes volatile state, and forced snapshot transfers.
  • Executed 20,000 randomized failure schedules, covering roughly 420M simulated events and 17.3M client operations. Raft's own invariants, election safety, state-machine safety, and log matching, are asserted continuously, and a from-scratch Wing and Gong linearizability checker validates every client history against what a single correct server could have produced. Because a run is a pure function of its seed, any failure replays exactly.
  • Found and documented 8 real bugs, each preserved as a CI regression alongside the seed that reproduces it. The most serious was a state-machine safety violation: an InstallSnapshot covering only a prefix of the log truncated entries the follower had already acknowledged, which let a later and otherwise legitimate election overwrite an entry that was already committed. Reaching it required five rare conditions to align at a single instant, and exactly one seed in 20,000 did.
  • Shipped a production layer on a Tokio host with a single-owner event loop. Group commit batches everything drained in one pass of that loop into a single fsync, and exactly-once client sessions come from replicating a dedup table, which turns at-least-once delivery plus idempotent apply into exactly-once from the client's point of view. On a workload held at 100% reads, stale reads run at 13,517 ops/s, lease reads at 13,057 ops/s, and linearizable reads at 9,043 ops/s, so the strictest reads cost roughly 1.5× for the quorum round trip that ReadIndex requires.
  • Measured failover across 10 consecutive leader kills under a 32-connection load. Clients saw a median interruption of 2,141 ms, most of which is clients rediscovering the new leader rather than the election, which finishes in under a second. None of the 300,000 operations were lost, and full throughput returned roughly 3.5 seconds after each kill.

Quant Research Platform & C++ Event-Driven Backtesting Engine

Technologies: C++20, Python, pybind11, CMake, DuckDB, Parquet, FastAPI, Streamlit, SQLite, Docker, GitHub Actions

A research platform for market-microstructure data, built the way a production system would be. It ingests L2 order-book and trade feeds asynchronously and stores them as hive-partitioned Parquet behind a DuckDB SQL layer, which answers analytical queries 2.5 to 2.9 times faster than a pandas baseline because partition pruning and predicate pushdown let it skip the files and rows it can prove are irrelevant. On top of that sit a C++ limit-order-book replay engine, an event-driven backtester, and a statistical validation stack. The governing principle is that backtests make self-deception easy, so the platform is designed to make the honest path the default path. The included strategies exist to exercise the infrastructure, and no claim is made that they are profitable.

  • Wrote the limit-order-book replay engine in C++20, bound to Python through pybind11 with zero-copy NumPy views and the GIL released inside its hot loop, so other Python threads keep running while it works. It sustains 11.5M events per second against 23.7k for the pure-Python reference, a factor of roughly 488. A standalone C++ harness reaches 15.8M events per second, at 100 ns p50 and 200 ns p99 per apply() call.
  • Enforced bit-for-bit parity between the C++ engine and a readable pure-Python reference in CI, so a defect has to appear in two independent implementations to reach production. The synthetic simulator keeps its own copy of the order book, and tests assert that the replay engine reconstructs that exact state from the event stream alone.
  • Developed an event-driven backtester that models order latency, the market impact of walking the book, maker and taker fees, position limits, and an approximation of queue position within each L2 price level. After every run it verifies the accounting identity equity = cash + position × mid and reconciles cash against the fill log, so a bookkeeping error fails the run instead of surfacing as PnL.
  • Made leakage detection a failing test rather than a convention. Leakage is any path by which information from the future reaches a feature that is supposed to know only the past. The check is the prefix property: a feature computed on history truncated at a given time must match the same rows computed on the full history. That is verified mechanically, and the detector is itself tested against a deliberately leaky feature to confirm it catches one. Walk-forward and purged K-fold splits are verified for overlap, ordering, and purge-gap correctness.
  • Reported every metric after costs with a stationary-bootstrap confidence interval, and left no gross-PnL code path anywhere in the system, so the flattering number is not available to report by accident. The Streamlit dashboard leads with a warning whenever the Sharpe confidence interval contains zero, which is the case where the result cannot be distinguished from no edge at all. Supporting tooling includes a FastAPI service whose time-machine endpoint reconstructs the L2 book at any historical microsecond, a SQLite run registry, 55 tests, CI, and multi-stage Docker builds.

Time-Series ML Platform: Leakage-Safe Training, Evaluation, and Serving

Technologies: Python, PyTorch (DDP, AMP), Transformers, TCNs, scikit-learn, pandas/PyArrow, OmegaConf, FastAPI, Prometheus, Docker, pytest

A research platform for short-horizon prediction on noisy, regime-switching limit-order-book data, covering training, evaluation, and serving. It is not a trading bot. The goal is to measure a signal accurately, including when the accurate answer is an unflattering one, and most of the code exists to make that the default outcome rather than a matter of discipline. The deliverable is a controlled comparison across two datasets. On the first, where the planted signal is linear in the features, a logistic regression ties a Transformer, and the edge per trade is smaller than what trading costs in a real market. On the second, which differs only in that the direction of the next move depends on how long order-book pressure has already persisted, the sequence models pull ahead of every classical baseline. One harness, reporting a tie where architecture does not matter and a gap where it does.

  • Built a config-driven training system covering a Transformer encoder and a TCN with multi-horizon heads, focal loss with class weighting, mixed precision, gradient accumulation, a cosine schedule with warmup, checkpointing, early stopping, and DDP through torchrun. It predicts three-class midprice direction at 1, 5, 30, and 60 second horizons together with a forward realized-volatility bucket, from 41 causal microstructure features computed over 200k one-second order-book snapshots. The data comes from a regime-switching simulator rather than a licensed feed, which means anyone can run the repository and, more usefully, that the amount of signal present is known in advance. If the evaluation reports more skill than was injected, the pipeline is broken.
  • Enforced no-lookahead by machine check rather than by convention. Truncation invariance requires that features recomputed on data cut at time t stay bit-identical for every row at or before t. Shuffled-label retraining has to collapse to the majority-class rate, averaged over five permutations rather than one, because regime persistence makes a single draw of that statistic vary by about as much as the tolerance it is judged against. Splits carry a purge equal to the 60-second maximum label horizon plus a 60-second embargo, and the scaler and volatility-bucket edges are fit on training rows only.
  • Defended causality at the architecture level as well as in the data. The TCN normalizes per timestep instead of using GroupNorm or BatchNorm, which pool statistics across the length axis of an (N, C, L) tensor and would leak future information into the past through the normalization layer alone, a defect that no amount of careful splitting would catch because the data pipeline is blameless. A receptive-field test asserts that the output at step t is unchanged when every input after t is overwritten.
  • Surfaced three things the headline numbers hide. The 0.899 volatility AUC is almost entirely regime detection: sliced within a single regime it falls to between 0.281 and 0.551, landing below chance in two of them, where 99% accuracy comes from predicting the majority class while the ranking within the regime is anti-correlated with the truth. Direction behaves the same way, 0.738 in aggregate against 0.547 to 0.580 inside every regime. A transaction-cost sweep puts the Sharpe crossing zero at roughly 0.14 bps per trade against a turnover of 0.251, which is below what any real venue charges, so the signal is real and measurable but too small per trade to act on. The information coefficient rising to 0.42 at a 60-second horizon would be evidence of leakage on real data and is reported as a property of the generator, whose injected pressure process has a 140-second half-life.
  • Caught the project's own baseline comparison being invalid. Baselines were scored with five-fold walk-forward over the whole series while deep models were scored on the final split alone, which are different exams, and comparing them made logistic regression look like it beat the Transformer at 0.769 against 0.738. A matched-split harness put every model on the identical 29,774 held-out windows and the gap disappeared: logistic ties the Transformer at 0.738 on one-second direction and on every other head. The Transformer and TCN share no architecture yet land within 0.004 of each other on every task, which is what saturation against a ceiling in the data looks like rather than either model being clever.
  • Isolated that tie as a property of the data by generating a second market identical to the first apart from one added return channel, in which a two-state flow phase tilts the book while it runs and its effect on price reverses once the phase is more than 20 seconds old. The same observed imbalance then predicts opposite directions depending only on its age, which no point-in-time feature encodes and a 64-step window does. Scored on identical anchors, the classical baselines reach 0.812 AUC on five-second direction from the 41 features, 0.859 once two hand-engineered run-length features are added, and the Transformer and TCN reach 0.873 from raw windows without those features. The middle tier is the control that makes the result interpretable, and the same two features move the baselines by +0.001 on the linear dataset, so they are inert until the data actually contains path structure. An earlier version of the generator failed an oracle-feature check, scoring 0.672 against 0.673 for the plain features, which showed its apparent path dependence was really an ordinary level effect and that the construction had to be replaced.
  • Served checkpoints through a versioned registry whose promotion is atomic, with the scaler and label-bucket edges travelling alongside the weights so there is no train-serve skew. A FastAPI service exposes single and batch prediction with Prometheus latency histograms, benchmarked at 1.9 ms p50 for a single window on CPU and 2,774 windows per second at batch 64, with throughput regressing at batch 256, which is the saturation point worth knowing before setting a batching policy. A suite of 52 pytest tests covers the generator, feature causality, labels, splits, model shapes, loss and calibration identities, cost arithmetic, registry versioning, and every API endpoint.

Coursework Assistant: A Claude Code Workspace for Technical Coursework

Technologies: Python, Claude Code (Agent Skills), PyMuPDF, python-pptx, python-docx, Pillow, Markdown, SM-2 Spaced Repetition

A study system built as 20 Claude Code slash commands over a plain-Markdown workspace, covering everything between raw lecture material and exam day: ingestion, memorization tables, homework help, mistake tracking, and test prep. There is no database and no server. Every artifact is a file the user owns, and every command reads a per-class preferences file before doing anything, so the same tool produces different output for a proof-heavy math class and a project-heavy CS class instead of one generic format.

  • Ingestion renders PDF pages to images rather than relying on extracted text alone, so hand-drawn diagrams, annotated slides, and scanned pages are read rather than silently dropped. The operating rules direct the model to read those page images explicitly and to work long decks section by section instead of skimming a 60-slide file in one pass, since missing content is treated as the one failure mode the tool cannot recover from after the fact.
  • /memtable is the core command. For each topic it writes a plain-language explanation next to the precise technical statement, a two-column flashcard table, step-by-step problem procedures where the class calls for them, and a coverage check mapping every source page to a section, so nothing ingested goes silently unwritten.
  • Mistakes are logged in one fixed three-bullet format everywhere they occur: what the question was asking, what specifically went wrong, and one action to take next time. The system requires a cause diagnosis first, content gap, wrong method, execution slip, misread, or time pressure, since those lead to different fixes and "be more careful" is not accepted as an answer. /playbook later consolidates every logged mistake into one document grouped by cause and fix, while preserving any hand-written rules the user added between explicit markers.
  • /check reads a photo of the user's own handwritten work, normalizing rotation, scale, and HEIC format first, then follows their reasoning line by line to the first step that breaks rather than re-solving the problem for them. A different valid method is not flagged as an error, and correct work is confirmed rather than searched for a nitpick to justify the pass.
  • Spaced repetition is opt-in per class and implemented as an SM-2 schedule that reads flashcard rows directly out of the existing notes rather than copying them into a separate store, so editing a note edits the card. /testprep builds a day-by-day study plan from a coverage table and note triage, while /cram keeps only what must be recalled cold for one specific exam, deliberately narrower than the full notes it draws from.

Research Ops: An AI-CLI Toolkit for Academic Research Workflows

Technologies: Claude Code (Agent Skills), Python, YAML, Markdown, BibTeX, arXiv/DBLP

A toolkit that turns Claude Code into a research assistant for academic work, built the same way as the coursework project: no server, no database, just configuration, a set of skills, and a knowledge base of plain-Markdown notes the user owns. A profile.yaml describing the researcher's field, topics, venues, and agenda drives every one of the 19 skills, so a paper-discovery digest for one field and one for another are built from the same command but surface entirely different material.

  • Discovery skills stay grounded to the profile rather than generic trending lists: /scout produces a ranked digest of recent papers and releases in the user's stated areas, /conference recaps a venue down to the handful of accepted papers most relevant to that specific researcher, and /people maps who works on a topic.
  • /summarize deep-reads a single paper into a structured, permanently saved note that separates what the paper claims from what its evidence shows and requires an honest weaknesses section rather than an optional one. /lit-review organizes a field into threads running from seminal work to state of the art and ends in a concrete reading order.
  • /ideate generates research ideas grounded in the user's own agenda and notes, runs an actual web search as a novelty check against each one, and can stress-test a saved idea in the voice of a skeptical reviewer. /recall answers questions only from the user's own knowledge base, citing the source file for every claim, and says plainly when it has nothing on a topic instead of filling the gap from general knowledge.
  • Writing skills are built around never inventing what they cannot verify: /draft leaves explicit [TODO] markers instead of fabricating a result, /cite pulls every BibTeX field from arXiv or DBLP rather than generating one from memory, and /rebuttal triages each reviewer point as concede or contest before drafting a response with placeholders in place of invented numbers.
  • The operating rules enforce this discipline system-wide: citations and BibTeX entries must be verified against a primary source, deadlines are checked against official venue pages rather than assumed, and every generated note is filed into the knowledge base with a matching index entry so /recall and /weekly stay accurate as the collection grows.
